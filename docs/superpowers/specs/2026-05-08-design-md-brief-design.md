# Design Spec: `design.md` as Pipeline Brief Source

**Date:** 2026-05-08
**Status:** Approved

## Problem

The Art Director outputs its daily design decisions as six separate delimiter-delimited blocks (`===HERO_COPY===`, `===HERO_RATIONALE===`, `===ARCHETYPE===`, `===CHASSIS_ID===`, `===VISUAL_SPEC===`, `===SELF_CHECK===`). Two failure modes stem directly from this format:

1. **Delimiter fragility** — runs 2 and 4 of the Art Director pipeline failed because the model lost a specific named block in a long structured response. Six blocks means six ways to fail.
2. **AD-intent vs. UD-execution drift** — the Unified Designer receives a visual spec blob injected into its prompt. Archetype directives (e.g., "phrase IS the page" for Specimen) are buried in prose. The UD defaults to conventional portfolio layout below the hero, ignoring the archetype constraint.

Additionally, there is no persistent, human-readable design brief that any agent can read cold. Site architecture, accessibility rules, and design methodology are buried in individual agent system prompts — not shared or composable.

## Solution

Introduce `design.md` as the single source of truth for the pipeline's design intent. The file has two layers:

- **Static layer** (`design.template.md`) — site architecture, accessibility rules, core methodology. Written once, maintained by hand, never touched by the pipeline.
- **Dynamic layer** — the `# Today's Design` section, generated by the Art Director each run and spliced into the template by the orchestrator.

The Unified Designer reads `design.md` as its complete brief. The static sections give it explicit constraints. The dynamic section gives it the AD's daily intent as a structured document.

---

## File Format

`design.md` lives at the project root. YAML frontmatter + four top-level sections.

```markdown
---
version: 1
name: doug-march.com
description: Daily-redesigned personal portfolio driven by environmental signals
---

# Site Architecture
[static]

# Accessibility Rules
[static]

# Core Methodology
[static]

<!-- DYNAMIC_SECTION_START -->
# Today's Design
[generated each run by Art Director]
<!-- DYNAMIC_SECTION_END -->
```

### Static Sections

**`# Site Architecture`** — routes, component hierarchy, SPA config, styling stack.
- Routes: `/` (index), `/about`, `/work/$slug`
- Components: `Layout.tsx`, `Sidebar.tsx`, route files per route
- Stack: TanStack Start SPA mode, PandaCSS for all styling, TypeScript strict
- Token entry point: `elements/preset.ts` (the AD writes this directly each run)

**`# Accessibility Rules`** — hard constraints, not guidelines.
- WCAG AA minimum contrast: 4.5:1 for body text, 3:1 for large text and UI components
- Minimum font size: 12px for any rendered text (not internal tokens)
- Hero phrase: unconstrained size, but must meet 3:1 contrast against page background
- Responsive: layout must not break at 375px, 768px, 1280px, 1440px viewports
- Semantic HTML: `<h1>` for hero phrase, `<nav>` for navigation, `<main>` for primary content

**`# Core Methodology`** — the design constitution. Defines archetypes as contracts.
- Hero-phrase-first doctrine: one quotable phrase anchors every design decision
- 8 archetype definitions written as compliance contracts (not descriptions)
- Chassis system: 5 chassis, selection criteria, affinity matrix
- Signal integration philosophy: how environmental signals translate to design choices
- Forbidden hue range: 90°–240° (green-blue-purple band, reserved)

### Dynamic Section: `# Today's Design`

The Art Director writes this section as a structured markdown document:

```markdown
## Today's Design — YYYY-MM-DD

### Identity
- **Hero Copy**: "the phrase"
- **Archetype**: Poster
- **Chassis**: big-shoulders-atkinson

### Color Palette
| Token         | Value     | Role                     |
|---------------|-----------|--------------------------|
| accent.dark   | #D91828   | Hero phrase color         |
| neutral.50    | #F9F2E8   | Page background           |
| ...           | ...       | ...                       |

### Typography
Layout-specific type decisions — sizes, weights, letter-spacing, line heights for the hero, body, labels.

### Layout Specification
CSS grid/flex structure, major dimensions, component placement. Written as concrete values the UD implements directly.

### Signal Integration
How each active signal appears in the UI — which component, what content, what style treatment.

### Rationale
The because-of chain: phrase → archetype → chassis → palette → layout. Each step explicitly justified.

### Self-Check
1. Hero quotability: Yes/No + reason
2. Because-of chain: Yes/No + reason
3. Render feasibility: Yes/No + reason
```

## Art Director Output Change

### Before
Six delimiter blocks in the AD's response:
```
===HERO_COPY===
===HERO_RATIONALE===
===ARCHETYPE===
===CHASSIS_ID===
===VISUAL_SPEC===
===SELF_CHECK===
```

### After
One delimiter block containing the full `# Today's Design` markdown section:
```
===DESIGN_MD_DYNAMIC===
## Today's Design — 2026-05-08

### Identity
- **Hero Copy**: "..."
- **Archetype**: Poster
- **Chassis**: big-shoulders-atkinson

[... rest of dynamic section ...]
===END_DESIGN_MD_DYNAMIC===
```

The `elements/preset.ts` file write is unchanged — the AD still writes it directly as a file action via the Claude CLI write tool, separate from the brief output. The Color Palette table in `===DESIGN_MD_DYNAMIC===` is a human-readable design spec (token names + hex values + roles); it is not the `preset.ts` source. The actual `preset.ts` TypeScript is written by the AD as a file action and is the authoritative token source for PandaCSS codegen.

### Why This Reduces Delimiter Failures

A 16KB response losing one of six specific delimiter strings is a documented failure mode (runs 2 and 4). A 16KB response failing to wrap a single markdown section it was already going to write in one delimiter pair is a significantly smaller risk. The model produces coherent markdown naturally. Six named blocks is six ways to fail; one wrapper block is one.

## Parser Changes (`scripts/utils/delimiter-parser.js`)

### Removed blocks
`HERO_COPY`, `HERO_RATIONALE`, `ARCHETYPE`, `CHASSIS_ID`, `VISUAL_SPEC`, `SELF_CHECK`

### Added block
`DESIGN_MD_DYNAMIC` — the full `# Today's Design` section as raw markdown.

### Extracted fields (from markdown, not separate blocks)
The orchestrator extracts machine-readable values from the `### Identity` section via regex:
- `HERO_COPY` — from `- **Hero Copy**: "..."` line
- `ARCHETYPE` — from `- **Archetype**: ...` line
- `CHASSIS_ID` — from `- **Chassis**: ...` line

### Validation (replaces current 6-block check)
1. `===DESIGN_MD_DYNAMIC===` block exists and is non-empty
2. `### Identity` section is present
3. `- **Hero Copy**:` line is non-empty
4. `- **Archetype**:` matches one of the 8 known archetype names
5. `- **Chassis**:` matches a chassis ID in the catalog

## Orchestrator Changes (`scripts/design-agents.js`)

### New assembly step — after Phase 1, before Phase 2

```
Phase 1: Art Director runs
  → validates DESIGN_MD_DYNAMIC block
  → extracts Archetype + Chassis ID from ### Identity
  → writes elements/preset.ts (unchanged)
  → [NEW] reads design.template.md
  → [NEW] replaces content between <!-- DYNAMIC_SECTION_START/END --> markers
  → [NEW] writes design.md to project root

Phase 2: Unified Designer runs
  → reads design.md as its complete brief
```

### Template assembly
- Read `design.template.md` from project root
- Find the `<!-- DYNAMIC_SECTION_START -->` / `<!-- DYNAMIC_SECTION_END -->` markers
- Replace everything between them with the parsed `DESIGN_MD_DYNAMIC` content
- Write to `design.md`

### Archive
`design.md` is copied to `archive/YYYY-MM-DD/build-TIMESTAMP/design.md` as part of the existing archive step. Replaces `brief.md` as the canonical build artifact (or kept alongside it during a transition period).

## Unified Designer Changes

### Before
The UD receives an injected visual spec blob in its prompt. Archetype compliance rules are not explicit.

### After
The UD prompt is restructured around `design.md`:

> "Read `design.md`. The `# Today's Design` section is your implementation target. The `# Site Architecture`, `# Accessibility Rules`, and `# Core Methodology` sections are your hard constraints. Where today's design spec and a methodology rule conflict, the methodology rule wins — implement the constraint and discard the conflicting spec detail silently."

### Impact on archetype compliance gap
The `# Core Methodology` section defines each archetype as an explicit compliance contract. Example for Specimen:

> *"Specimen: The phrase IS the page. No content below the hero fold except navigation. Any component that adds a project list, body copy section, or index below the fold violates this archetype and must be removed."*

The UD reads this definition alongside today's spec. The constraint is explicit, not inferred from spec prose. This directly addresses the run-1 failure where the UD honored the hero but added a conventional portfolio below it.

### Screenshot Critic
The Screenshot Critic can also read `design.md` to get the archetype contract definition when evaluating rendered output, rather than re-deriving it from the visual spec. The `# Core Methodology` archetype definitions become the grading rubric.

## Open Decisions for Implementation

1. **`design.md` gitignore or committed?** It's a generated artifact that changes daily. Options: gitignore (only template committed), commit daily (acts as a running record of the brief), or commit via the archive step only.

2. **`brief.md` in archive** — keep alongside `design.md` during transition, or replace it?

3. **`design.template.md` content** — the static sections (architecture, accessibility, methodology) need to be authored. This is real writing work, not just scaffolding.

4. **Awesome-design-md inspiration pull** — the user mentioned pulling from `github.com/voltagent/awesome-design-md` for inspiration. This could be: (a) format reference only (already incorporated), or (b) the pipeline fetches a relevant example at runtime to give the AD a style reference. To be scoped in implementation.
